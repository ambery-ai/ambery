# 错误处理模型

[English](errors.md) | 中文

> 本文定义 ambery 的错误呈现模型——错误即通知。不定义当前实现、协议或配置结构。

## 模型

错误 = 通知——用户从 UI 得知，仅此而已。错误不分种类，只分留存时长（瞬时 / 常驻）。`unconfigured` 同样是错误通知——持续存在、需要行动（配置）；只有显式的 `debug` mock 模式不产生通知。

## 来源

| 来源 | 留存 | action | 示例 |
|------|------|--------|------|
| LLM 调用失败 | 瞬时 | — | 单次调用的 HTTP 错误 / 超时 |
| LLM 初始化失败 | 常驻 | setup | active provider 配置损坏（无 key / 空 base_url） |
| 消息入队失败 | 瞬时 | — | queue 满 |
| key 写入失败 | 瞬时 | — | env 文件不可写 |
| core 不可达 | 常驻 | — | 后端离线 |
| unconfigured | 常驻 | setup | 未配置 LLM |

## 呈现

两个出口，各对应一种留存：

- **气泡**（chat 流）——瞬时："这一轮发生了什么"。一次一报，取走即清。
- **banner**（chat 顶部）——常驻："系统需要你注意"。留存为常驻的错误事件打开，保持到手动关闭。action 可选：有 → 点击分派到目的地；无 → 纯常驻告知（只能关闭）。同屏最多 2 个——每个条件一个（同条件的重复事件不额外占槽）；超出的条件排队，关闭任一后顺延补位。

常驻性由出口提供，不靠独立的状态值：同一个错误事件同时打开瞬时气泡与常驻 banner。持续的条件必须到达常驻出口——只走瞬时气泡，持续条件只会被看到一次然后静默。

Card 属于组件渲染通道，不是错误出口。

## 通道

```
 错误源（任一，见上表）
      │
      ▼
error 事件 { message, retention, action? }
      │
      ├─ 常驻 ──► banner（≤2 槽、每条件一个、超出排队、
      │             关闭顺延补位；action? 可选——有则点击分派，无则纯告知）
      └─ 瞬时 ──► 气泡（一次一报、取走即清）
```

所有错误都以 `error` 事件走事件通道。每个事件携带 `message`（用户可见文案）、`retention`（`transient` / `persistent`），以及可选的 `action`——目的地 id（初版：`setup`，设置引导）。前端按留存路由：常驻 → banner，瞬时 → 只出气泡；action（若有）决定 banner 的点击行为。来源不属于契约——前端永不按来源分支。

持续条件在自身变化点被发出（启动 / 配置或 key 变更 / 调用结果），不逐轮重发；banner 对重复事件幂等（已开不重开）。
